# AI駆動開発オーケストレーション

タスクの種類に応じてスキルとサブエージェントを使い分け、効率的に開発を進める。

## 基本原則

1. **メインエージェントはオーケストレーター**: 設計判断・タスク分解・品質レビューに集中する
2. **実装はサブエージェントに委譲**: コンテキスト汚染を防ぎ、各サブエージェントが専門スキルをフル活用する
3. **1サブエージェント = 1責務**: バックエンド実装とフロントエンド実装を同じサブエージェントに混ぜない
4. **メインは実装コードを直接編集しない**: `backend/` と `frontend/` のコードは必ずサブエージェント経由で変更する

## 作業開始時の手順

1. `git status` で現在のブランチと状態を確認
2. `docs/refactoring/09-progress.md` で次のタスクを特定
3. master でテストが通ることを確認してから作業開始
   - `docker compose exec backend ./gradlew test`
   - `docker compose exec frontend pnpm test`
   - 壊れていたら先に修正

## サブエージェント一覧

| エージェント | 責務 | 使用スキル |
|---|---|---|
| `openapi-design` | API 仕様の設計・更新 | `openapi-spec-generation` |
| `backend-domain` | Domain + Application 層の実装 | `clean-ddd-hexagonal` + `kotlin-springboot` |
| `backend-infra` | Infrastructure + Presentation 層の実装 | `kotlin-springboot` |
| `frontend-impl` | ページ・コンポーネント・Route Handler | `frontend-design` + `vercel-react-best-practices` |
| `docker-infra` | Docker・CI/CD 設定 | `docker-expert` |
| `git-operations` | コミット・ブランチ・PR 作成 | `git-commit` |

## 委譲の判断基準

### メインが直接やるケース

- 設計ドキュメントの読み込み・判断
- タスクの分解・優先順位付け
- サブエージェントの結果レビュー
- ドキュメント（`docs/`, `AGENTS.md`, steering）の更新
- 進捗ファイル (`09-progress.md`) の更新
- ビルド・テストの実行と結果判断
- 1-2ファイルの確認で済む軽微な調査

### サブエージェントに委譲するケース

- バックエンドのコード変更（規模に関わらず）
- フロントエンドのコード変更（規模に関わらず）
- Git 操作（コミット、push、PR）
- Docker/インフラの変更
- OpenAPI 仕様の変更

### context-gatherer に委譲するケース

- 3ファイル以上を横断して読む必要がある調査
- 影響範囲が不明で探索的に調べる必要がある場合
- バグの原因特定で複数レイヤーを追う場合

## タスク分解の考え方

### API 変更を伴う場合（順序厳守）

1. **API 仕様を先に確定** → `openapi-design`
2. **バックエンド実装** → `backend-domain` → `backend-infra`（順序あり、後述）
3. **フロントエンド実装** → `frontend-impl`

API が契約（SSoT）なので、先に確定させてからバックエンド・フロントエンドがそれぞれ独立して実装できる状態を作る。

### バックエンド内の依存チェーン

`backend-domain` → `backend-infra` は必ずこの順序で実行する。

1. `backend-domain` が Port（インターフェース）とユースケースを実装
2. メインが作成されたファイルを確認（パス・シグネチャ）
3. `backend-infra` に以下を `contextFiles` で渡す:
   - 実装すべき Port のファイルパス
   - 関連する設計ドキュメント
   - 必要に応じて Domain モデルのファイルパス

### API 変更を伴わない場合

- 影響範囲に応じて該当エージェントに直接委譲する
- バックエンドのみ、フロントエンドのみなら1エージェントで完結

### バグ修正

1. 原因調査: メインが行う（`context-gatherer` を活用）
2. 修正実装: 該当レイヤーのエージェントに委譲
3. 検証: メインがビルド・テストを実行

## サブエージェントへの指示に含めるもの

1. **スキル活用指示**: どのスキルを有効化するか
2. **参照ドキュメント**: 具体的なファイルパスを `contextFiles` で渡す
3. **成果物の期待**: 何を作成/変更するか明確に
4. **制約**: やってはいけないこと（例: 他コンテキストのコードを変更しない）

具体的なテンプレート例は `#orchestration-templates` で参照可能。

## エラーハンドリング

### サブエージェントがビルドエラーで失敗した場合

1. エラーメッセージを添えて同じエージェントに再委譲（最大2回）
2. 2回失敗 → メインが原因を分析し、アプローチを変えて再指示
3. 設計レベルの問題が判明 → 設計ドキュメントを修正してから再委譲

### テストが通らない場合

1. 失敗したテストの内容を確認
2. 実装の問題か、テスト自体の問題かを判断
3. 該当エージェントにエラー内容と修正方針を添えて再委譲

### サブエージェントが想定外のファイルを変更した場合

- 変更を revert し、制約を明確にして再委譲する

## コンテキスト管理のルール

1. **メインセッションではスキルを有効化しない**: スキルはサブエージェントが使う
2. **メインセッションの役割**: 設計判断、タスク分解、サブエージェント結果のレビュー
3. **サブエージェントは独立**: 他のサブエージェントの結果に依存する場合、メインが中継する
4. **設計ドキュメントはメインが読む**: サブエージェントには必要な情報を `contextFiles` で渡す
5. **広範な調査は `context-gatherer` に委譲**: メインのコンテキスト消費を抑える
6. **ビルド・テスト実行はメインが行う**: 結果の判断とフィードバックはメインの責務

## 品質ゲート

サブエージェントの成果物をマージする前に、メインエージェントが以下を確認:

- [ ] `docs/backend/AGENTS.md` のルールに違反していないか
- [ ] `docs/frontend/AGENTS.md` のルールに違反していないか
- [ ] SSoT ルールに違反していないか（情報の重複がないか）
- [ ] ビルド・テストが Docker コンテナ内で通るか
- [ ] 想定外のファイル変更がないか（`git diff --stat` で確認）
